# Baseline — 2026-11-11

Build: `examples/hello-gpu`, release profile, wgpu 30.0.1, Rust 1.92.0, NDK 27.1.

## What could be measured

No Android device, emulator or Xcode installation was available, so this report contains build-artifact sizes only. No runtime figure appears here because none was measured.

| Artifact | Size |
| --- | --- |
| `libhello_gpu.so`, arm64-v8a, debug info stripped | 5,764,336 bytes (5.50 MiB) |
| `libhello_gpu.so`, x86_64, debug info stripped | 5,694,904 bytes (5.43 MiB) |
| `app-debug.apk` (both ABIs, debug Java host) | 17,038,050 bytes (16.25 MiB) |

Before the rectangle pipeline and touch input were added (clear colour only), the same artifacts were 5,233,728, 5,207,064 and 11,337,329 bytes. The libraries grew by about 0.5 MiB each, probably because the first pipeline pulls in shader translation code that a clear does not need (not confirmed). The APK grew by 5.4 MiB, far more than the two libraries (1.0 MiB together). Its zip entries total only 12.3 MB (libraries stored uncompressed, plus dex), so about 4.7 MB of the file is outside the entries (alignment padding or signing data). That has not been explained and should be before a release APK is measured.

Almost all of the library is wgpu and its shader compiler (naga); the application and Morningstar's own code are a few thousand lines. Two things to try, each to be measured: `opt-level = "s"` for the GPU crate's dependencies, and whether the GLES backend is worth its size as a Vulkan fallback.

The debug APK's `classes.dex` is 2.4 MB although the host is two small Java classes; find out what AGP is bundling before measuring a release APK.
