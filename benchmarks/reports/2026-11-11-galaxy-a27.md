# Samsung Galaxy A27 — 2026-11-11

First measurements on a real device. One device, one session, working tree uncommitted: treat as a first reading, not a rigorous baseline.

| | |
| --- | --- |
| Device | Samsung SM-A276B (Galaxy A27), SoC SM6475, Adreno 710 |
| OS | Android 16 (API 36) |
| Display | 1080x2340, running at 120 Hz |
| Backend | Vulkan (Qualcomm Adreno driver, build dated 02/04/26) |
| Build | `examples/hello-gpu` (tap counter, 51 rounded rectangles per frame), release Rust library in a debug APK |
| Method | `benchmarks/android/measure.sh 3`, device on USB, not in airplane mode, brightness not fixed |

## Results

| Metric | Value |
| --- | --- |
| Cold start, `am start -W` TotalTime | 359, 350, 362 ms (a second session's third run: 366 ms) |
| Frame interval, p50 | 8.32 to 8.34 ms in every window (the 120 Hz period is 8.33 ms) |
| Frame interval, p95 / p99 | 8.75 to 8.88 ms / 9.08 to 10.62 ms |
| Frame interval, max | 9.36 to 13.60 ms across six 480-frame windows |
| CPU per frame (app + encode + submit), p50 / p95 / p99 | 0.79 / 0.93 to 1.05 / 1.24 to 1.44 ms |
| Present call, p50 / p95 | 2.6 to 3.1 / 4.9 to 5.7 ms |
| Memory, total PSS | 80 to 84 MB |
| Memory, Graphics / Native Heap | 31.2 MB / 13.8 MB |

Over 30 seconds (3,600 frames) no window recorded a frame interval of two refresh periods (16.67 ms), i.e. no clearly dropped frame, apart from start-up. The first window after a cold start had one 7 ms CPU outlier.

## Reading these numbers

- **CPU per frame is about 9% of the 8.33 ms budget** at the median, for a trivial scene. This is the floor, not a result to celebrate: there is no text, layout or image work yet.
- **The present call takes longer than everything Morningstar does.** Whether that time is the driver waiting for the display or real work is not known. An earlier build counted it as CPU time and reported a 3.4 ms median, which was misleading; the two are now reported separately.
- **80 MB PSS is high for an app that draws rectangles.** 31 MB is graphics memory (swapchain images at 1080x2340 account for part). The rest has not been broken down. Worth a look before it is taken as the baseline to defend.
- **The app redraws every vsync even when nothing changes**, so these figures also describe its idle state. That is a known battery cost (ADR 0004).

## Functional checks made in the same session

- The picture on the device matches the desktop Metal render (inspected by screenshot): same layout, rounded shapes, smooth edges.
- Touch reaches the app: taps on the button incremented the tally.
- Backgrounding and returning recreated the surface in the same process and the frame count continued.

## Addendum: after text rendering was added (same day, same device)

Scene: one rounded rectangle and about 150 glyphs. Three consecutive 480-frame windows after launch, while the screen was being tapped:

| Metric | Value |
| --- | --- |
| Frame interval, p50 | 8.31 to 8.35 ms |
| Frame interval, p95 / p99 | 11.2 to 11.5 ms / 12.4 to 14.7 ms |
| Frame interval, max | 13.4 to 21.2 ms (one window exceeded two refresh periods) |
| CPU per frame, p50 / p95 / p99 | 0.77 to 0.85 / 1.20 to 1.73 / 1.90 to 4.42 ms |
| Present call, p50 | 0.41 to 0.48 ms |
| `libhello_gpu.so`, arm64-v8a | 9,534,352 bytes (was 5,764,336), including about 1.5 MB of embedded fonts |

Median CPU cost is unchanged by text. The tail is worse: p95 frame interval rose from about 8.8 to about 11 ms. This was measured while the count was changing, which rasterises new glyphs and re-uploads the whole atlas; that is the suspected cause and has not been isolated. It was not measured with the screen left alone, and conditions differ from the earlier run (the present call's median also dropped from about 2.8 to 0.45 ms for reasons not investigated), so the two runs are not a controlled comparison.

## Not measured

GPU time, energy, input latency, a low-end device, a release APK, and anything on iOS.
