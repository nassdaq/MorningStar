Testing

An app is tested on the development machine, with no phone and no server. That is possible because the app never does I/O: it asks for work as data, and a test can look at the request and answer it.

The kinds of test

TestShowsWhere
A journeyThat tapping, typing and answers lead to the right state and screentests/e2e.rs
An accessibility checkThat no screen has a control without a label, a small target or low contrasttests/accessibility.rs
A picture of each screenThat a screen still looks as it did when you last accepted ittests/screens.rs
A fidelity testThat a screen matches the design's picture to within a measured limittests/fidelity.rs in the designed examples
Pixel tests of the rendererThat each drawing operation produces the right pixels on a real GPUcrates/morningstar-gpu/tests
cargo test -p my-app          # one app
cargo test --workspace        # everything, including the tests that draw on the GPU

Answering in the phone's place

Ui::testing(app) holds every request the app makes instead of sending it. The test reads it and answers.

#[test]
fn the_server_is_asked_once_and_its_answer_is_kept() {
    // `Ui::testing` holds every request instead of sending it.
    let mut ui = Ui::testing(Orders::default());
    ui.send(Message::Refresh);
    assert!(ui.app().loading);

    // What the app asked for, as data.
    let pending = ui.pending_effects();
    assert_eq!(pending.len(), 1);
    let ServiceRequest::Http(request) = &pending[0].request else {
        panic!("expected a request");
    };
    assert_eq!(request.url, format!("{SERVER}/v1/orders/latest"));

    // The test is the server: "it replies this".
    assert!(ui.answer_http(Ok(HttpResponse::new(200).with_body("Order 1042"))));
    assert!(!ui.app().loading);
    assert_eq!(ui.app().status, "Order 1042");
    assert_eq!(
        ui.stored(LAST_ORDER),
        Some("Order 1042"),
        "kept on the phone"
    );
}

#[test]
fn no_connection_is_a_sentence_not_a_crash() {
    let mut ui = Ui::testing(Orders::default());
    ui.send(Message::Refresh);
    assert!(ui.answer_http(Err(HttpError::Offline)));
    assert_eq!(ui.app().status, "No connection.");
    assert_eq!(ui.stored(LAST_ORDER), None);
}

Stored values and the install id are given as the phone would have them:

#[test]
fn a_value_stored_on_an_earlier_run_is_there_at_setup() {
    // The phone as the app finds it: an install id and stored values.
    let host = HostState::new().with_stored(LAST_ORDER, "Order 1041");
    let mut ui = Ui::testing(Orders::default());
    let _frame = morningstar::Frame::for_app_with_host(&mut ui, &host);
    assert_eq!(ui.app().status, "Last time: Order 1041");
}

A finger and a keyboard

A journey taps where a widget was laid out and types through the same interface the keyboard uses. A generated app has a small Device in tests/support/mod.rs that does both:

let mut device = Device::fresh();
device.tap("open-settings");          // the widget with .id("open-settings")
device.tap("name");
device.type_text("Ada");
device.tap("save");
assert_eq!(device.app().name, "Ada");

Tapping by id sends real pointer events to where the widget was laid out, so layout and hit testing are part of every journey. ui.rect_of(id) is where a widget was laid out, ui.visible_rect_of(id) the part that shows, and ui.overflows() lists boxes whose children do not fit.

Pictures

tests/screens.rs renders each screen and compares it with a reference picture in tests/references/. The first run writes the references; look at them and commit them. When a visual change is one you meant, accept it:

MORNINGSTAR_UPDATE_REFERENCES=1 cargo test -p my-app

A passing test does not show that a screen looks right, only that it has not changed. After changing anything visual, render it and look:

cargo run -p my-app --example screenshot -- out/

Holding a screen to its design

The designed examples compare every screen with the design's own picture and fail if more than a measured share of pixels differs. Barua Talk's limits, with what was measured:

ScreenMeasured differenceLimit
Home0.0847%0.10%
Room0.6900%0.70%
Incoming call0.0154%0.05%
Video call0.2860%0.30%
Phone call0.0499%0.05%

Design to code is the method, and morningstar-diff the tool.

In CI

The workflow in .github/workflows/ci.yml runs formatting, lints, the tests that need no GPU, the Android lints and the servers' tests on every push. The job that runs every test on a GPU is started by hand. ADR 0043.

The API a test uses is in the Ui reference.
